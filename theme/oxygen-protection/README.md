# Protective marking on every published page (issue #175)

Puts a protective-marking bar at the **top and bottom of every page** of the
Oxygen WebHelp output, with the marking text supplied as a **publishing
scenario parameter** rather than baked into the template.

Before this overlay the published output carried **no marking at all**: a full
`main` publish (221 pages) contained zero occurrences of any marking, and the
footer read *"Generated by &lt;oXygen/&gt; XML WebHelp"*.

## Why a parameter and not just markup

This is the decisive point, and it is not about flexibility.

The delivered target sits behind a **one-way air-gap gateway**, so every
template defect costs a full transfer cycle. Following Fi3ldMan's transfer
procedure (`context-docs/12-template-transfer-air-gapped-network.md`):

| Change | Needs a re-transfer? |
| --- | --- |
| Any edit to CSS, XSLT, page layouts, fragments or the `.opt` | **Yes — full package** |
| **A different protective marking or banner colour for an export** | **No — scenario parameters** |

So the one thing that plausibly changes per export — the marking — is the one
thing that must *not* live in the template. A CSS-only banner looks cheaper and
is in fact the expensive option: every marking change would become a full
package rebuild and another gateway crossing.

## The three parameters

Declared in `pptx-transform.opt`, overridable per transformation scenario:

| Parameter | Ships as | Meaning |
| --- | --- | --- |
| `webhelp.show.protection` | `yes` | Only the literal `yes` emits the bars |
| `webhelp.protection.text` | `COMMERCIALLY SENSITIVE` | The marking |
| `webhelp.protection.background.color` | *(empty)* | Empty = the fixed colour in `protection.css`; set it to override per export |

**The marking is identical in both editions.** It describes the material, not
the audience, so both scenarios take the same values and there is no
per-edition variation to configure.

There is deliberately **no fail-fast on an unset `webhelp.show.protection`** —
the template ships with it set, and that is sufficient.

## What's here

```text
oxygen-protection/
├── page-templates-fragments/
│   ├── protection-header.xml   ← empty <header class="wh_header_protection"/>
│   └── protection-footer.xml   ← empty <footer class="wh_footer_protection"/>
├── resources/
│   └── protection.css          ← the one fixed colour, light mode and dark
└── xslt/inc/
    └── customProtection.xsl    ← fills (or drops) the two placeholders
```

## How it works

1. Two fragment files each declare **one empty placeholder element**, and the
   template binds them to `webhelp.fragment.before.body` and
   `webhelp.fragment.after.body`.
2. `customProtection.xsl` matches those elements in `mode="copy_template"`,
   reads the parameters via `oxyf:getParameter(...)`, and either fills the
   element with the marking text or drops it entirely.
3. `protection.css` paints them.

Both placeholders are included on **all four** generated page types — main
/tiles, topic, search results, index terms — which is what makes the marking
unmissable. That matters: issue #178 was exactly a customization that reached
only the pages built from a topic.

Fragment content included via `<whc:include_html>` is re-processed in
`copy_template` mode by Oxygen's own `commonComponentsExpander.xsl` (see its
`includeCustomHTMLContent` template), which is what allows the XSLT to match
inside a fragment file rather than a forked page layout.

### Note the `<html><body>` wrapper in the fragment files

`includeCustomHTMLContent` copies only `<body>`'s children when it finds that
wrapper, and copies the **whole document — comments included** — when it does
not. Without the wrapper, each fragment's explanatory comment would be emitted
into every published page.

### Divergence from Fi3ldMan: no forked page layouts

Fi3ldMan hosts the same placeholders in **forked copies of `header.xml`,
`footer.xml` and all four `wt_*.html` page layouts**, and its README is blunt
about the consequence: every custom `page-templates/*` file must be re-diffed
against stock on each Oxygen upgrade.

Binding to the `before.body` / `after.body` fragment points instead gets the
same two bars on the same pages with **no forked page layouts at all**, so this
template stays stock-plus-parameters. Two further consequences:

- Oxygen's own `<footer class="wh_footer">` **survives**; the marking bar is
  appended below it rather than replacing it. (Fi3ldMan replaces it, which is
  why the stock `webhelp.fragment.footer` extension point has no effect in
  their template. It would work here — the placeholder route is used anyway,
  because it is what makes the conditional and the colour override possible.)
- On an Oxygen upgrade there is nothing to re-diff. Re-check only that the
  `webhelp.fragment.before.body` / `after.body` placeholders still appear in
  all four stock `wt_*.html` layouts.

## Colour

One fixed colour in **both light and dark mode** — background *and* text both
pinned to literals in `protection.css`, neither inheriting a theme token, and
no `[data-wh-theme="dark"]` variant. The template runs with
`webhelp.enable.dark.mode=yes`, and a marking that changes colour with the
theme is a marking you cannot describe in a handling instruction.

`#bfebb9` on black, matching Fi3ldMan and this project's own previous output.
A scenario override arrives as an inline `@style`, which beats the stylesheet;
the text stays black, so choose a light enough override.

## Already done for you in `theme/pptx-transform/`

If you publish with this repo's own template, this is **already wired in** —
payload files copied in, parameters declared, XSLT bound to all four extension
points, `protection.css` loaded last. Point both scenarios at
`pptx-transform.opt` and publish.

## Wiring it into a different template

1. Copy `resources/protection.css`, `page-templates-fragments/protection-*.xml`
   and `xslt/inc/customProtection.xsl` into that template.
2. Declare the three parameters in its `.opt`.
3. Add `<css file="resources/protection.css"/>` **last** in `<resources>`.
4. Bind the two fragments:

   ```xml
   <fragment file="page-templates-fragments/protection-header.xml"
             placeholder="webhelp.fragment.before.body"/>
   <fragment file="page-templates-fragments/protection-footer.xml"
             placeholder="webhelp.fragment.after.body"/>
   ```

5. Import `inc/customProtection.xsl` from a stylesheet bound to **each** of
   `com.oxygenxml.webhelp.xsl.createMainPage`,
   `com.oxygenxml.webhelp.xsl.dita2webhelp`,
   `com.oxygenxml.webhelp.xsl.createSearchPage` and
   `com.oxygenxml.webhelp.xsl.createIndexTermsPage`. Miss one and that page
   type publishes unmarked.

Do **not** override `<whc:page_libraries>` in those stylesheets — Fi3ldMan's
Oxygen 2024 template did, and that is what broke its output under Oxygen 2026.

## Dev/CI preview

`scripts/publish_html.py` reads `webhelp.protection.text` and
`webhelp.show.protection` **out of `pptx-transform.opt`** and stamps the result
on `<body data-protection="…">`; the preview theme renders it via `attr()` at
the top and bottom of every page. One source of truth, so the preview cannot
state a different marking from the delivered output. If the template is missing
or the marking is switched off, the preview publishes **unmarked and warns** —
a wrong marking is worse than a missing one.

## Scope

WebHelp only. The `.opt`'s `<pdf>` section is untouched; whether PDF output
should carry the marking is unconfirmed.
